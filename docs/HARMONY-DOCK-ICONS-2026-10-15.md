# Unopened Harmony app shortcuts: icon and name repair

User Test 4.1 showed generic executable tiles named `PowerEmuGuestApp` for selected Address Book and Captain Polliwog shortcuts. Neither app was running. The session helper's executable filename was constant, and icon requests required a running guest PID. No icon file existed for those unopened apps. Runtime display-name SPI alone was not a sufficient fallback.

## Changes

- Selected helpers use a bounded sanitized guest app name as their executable filename. The copied signed executable's code bytes remain unchanged. The existing display-name setter remains an optional enhancement.
- Tools accepts a bounded `APPPATHICON` request for an installed app bundle without launching it. Both sides validate path/format/size; guest lookup checks the same fresh shallow installed-app inventory and resolves symlinks within the allowed application roots.
- A declared valid bundle-contained ICNS is preferred over LaunchServices' cached icon. Captain Polliwog's icon resource was present and decodable in Tiger, but LaunchServices returned the generic application image. Direct declared-resource rendering fixes that case. Existing PID-based APPICON remains compatible.
- Icons are rasterized to 128×128 PNG and cached by canonical VM package plus exact guest app path. Cached images are available immediately on a later session, with one refresh per Tools connection. Duplicate image replies do not restart the helper. Selected helpers now draw an explicit Dock image view as well as setting the application icon.
- Tools reconnect resets pending icon requests, so installing the updated Agent while the new host is running allows a fresh icon query. Receiving an icon never opens the guest app.

## Evidence

The release host build and isolated gcc-4.0/10.4u PPC Agent compile passed. The signed native runtime fixture verifies selected helper localized name and filename, unopened path-icon requests, valid/invalid image handling, exact session routing, no launch on creation, unchanged helper bytes/signatures, VM-specific cache isolation, cache restoration, no PID change on repeated identical icon or running-app updates, and cleanup.

Owned independent-clone run PID 96509 collected both path icons while Address Book and Captain Polliwog remained closed. Address Book returned 23,561 bytes at 128×128, SHA-256 `2e98174297be920034364643a887fd87d786f8db1b8531d4ae41ba5f95e53ed0`. Initial Captain lookup reproduced Tiger's generic image. A read-only declared-icon fixture (with NSApplication initialized) rendered the correct Captain artwork from its declared `CaptainPolliwog.icns`, 30,880 bytes. The initial fixture without NSApplication produced no image and was rejected; it is not evidence for the fix. The final production Agent was then temporarily installed in the same owned run; its full request/reply produced byte-identical correct Captain artwork at the host cache. No Address Book or Captain Polliwog launch was needed. Helper filenames were `Address Book` and `Captain Polliwog` and their signed code bytes matched the source helper.

The original guest Agent and Info.plist were restored exactly (original binary MD5 `a48b78f5f35a2a9ff707f7ad6d77a0f4`), the owned run stopped before its 480-second guard, and the private configuration/selections were restored. No commands were sent to the user's VM for this icon test, and no running app bundle was modified. Actual host Dock pixel capture was unavailable through the active desktop controls; the checks cover registered helper names, explicit Dock image content, decoded PNG artwork, routing, signatures and lifecycle rather than claiming a separate Dock screenshot comparison.

## Test 4.3 — focus control-thread isolation

The user clarified that the guest stayed usable outside Harmony; its proxy windows stopped refreshing and re-entry failed after reordering an existing host Dock icon. The exact Dock gesture is not yet reproduced. Dock routing review found activation can change the guest front app but no direct reorder-to-Harmony-disable path.

Enabled the existing bounded focus worker alongside the tested menu/background workers in the shipped Agent resource plist. This moves FOCUSWINDOW Accessibility lookup/raise/confirmation off the control thread. Connection/session/Harmony epoch, target owner, geometry and front-process checks still gate activation/acknowledgement. Pending work is replaceable and bounded. The worker cannot cancel an AX call already executing; it can remain occupied until that app responds. Explicit RAISE/RAISEHARD/MOVEWINDOW/MINIMIZE/UNMINIMIZE and periodic CGS calls remain separate risks; this is not a blanket freeze fix. Added an effective-worker startup LOG and replaced the misleading no-ack reinstall advice with save-work/restart guidance.
