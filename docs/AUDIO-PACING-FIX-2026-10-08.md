## Confirmed cause and fix

In `hw/audio/screamer.c`, `screamer_pace_cb` calculates fractional sample allowance using elapsed virtual time. A dispatched QEMU timer is no longer pending. Completing a DBDMA descriptor synchronously invokes `dbdma_end`, then `channel_run`, then `pmac_screamer_tx` for the next descriptor. The TX entry point treats a nonpending pacer as an idle clock and resets `pace_frac` to zero. The reset silently discards a fraction of a frame on many ticks.

Arm the next pacer tick **before transferring DMA**, so synchronous descriptor continuation sees the clock as running. Remove the old end-of-callback arm. Explicitly delete the prearmed timer on the existing idle-stop branch. Guest sample rate, clock ownership, 1 ms pacing interval, DMA contents and BQL ownership are unchanged.

`tests/poweremu/screamer-pacing-test.py` extracts the actual pacer and TX/RX entry points and reproduces synchronous descriptor chaining with QEMU's timer-dispatch semantics. The same pacer now distinguishes host backpressure from DMA inactivity: pending TX/RX work keeps its timer armed even when no frames move, so a full host queue cannot permanently strand a descriptor. A 500 ms full-queue/recovery regression passes; genuine DMA idle still stops after 200 ticks.

Exact frame conservation passes over 10,000 irregular ticks at 22.05, 32, 44.1 and 48 kHz, TX-only and duplex, idle stop/restart, with ASan/UBSan. Saved pre-fix source fails the conservation assertion.
